# Healing Rain — 레시피 중심 제작 스튜디오

## 구현 범위 (2026-10-12)

메뉴: 일본 BGM 스튜디오 바로 아래, /healing-rain.
레시피 라이브러리 → 장면 설계 → 제작 계획. 10개 레시피(침대 열차, 숲속 텐트, 한옥, 오두막, 외딴 자연, 한적한 공원, 산사, 연못, 호수, 고산 마을).
서버 POST /api/healing-rain/plan은 허용된 설정을 검증하고 이미지·영상·음향 프롬프트를 컴파일한다. 외부 생성 호출, 과금, 업로드는 없다.
로그인 계정 저장과 브라우저 초안 저장을 구분한다. 계정 저장은 인증된 API에서 프롬프트를 다시 컴파일하고 소유자별 불변 스냅샷으로 보관한다. 같은 요청 ID 재시도는 중복 저장하지 않는다. 브라우저 초안은 명시적으로 계정에 가져올 수 있으며 원본을 지우지 않는다. JSON 내보내기도 지원한다.
카드에는 AI 생성 실사 대표 이미지를 사용한다. 설정 변경의 실시간 결과가 아님을 표시한다. 10개 WebP를 직접 제공해 이미지 최적화 경로의 일시적 누락을 피한다.

## 핵심 모델

- Recipe: 고정 컨셉, 소재/청취 위치, 음향 레이어, 움직임/루프 규칙, 버전.
- Project: 레시피 스냅샷, 사용자 연출, 강도/천둥, 팔레트/카메라/소품, 최종 길이.
- Generation: 프로젝트 전용 신규 원본, 모델/요청/비용/외부 job ID, 상태 및 출처.
- Edit: 영상·오디오 원본 참조, 구간/게인/크로스페이드, 천둥/번개 이벤트, 출력.
- Review: 연결 청감, 영상 이음새, 변형, 클리핑/무음, 실질적 작품 차이.

매 프로젝트 신규 자산 생성이 기본이다. 기존 음원은 레시피 미리듣기 참고 자료로 쓰고, 생성된 결과는 제작 이력에 보존한다. 기존 HealingRain의 SQLite와 WAV는 이동하거나 덮어쓰지 않는다.

## 2026-10-13 — 회차 기획과 인트로 다양성 백엔드 v1

### 목적과 현재 범위

하나의 소재를 반복 생성하는 대신, 인트로·본편 풍경·빗소리·전환의 연결 의도를 회차 단위로 남긴다. 같은 본편의 제목·색상·시드·인트로만 바꾸면 반복 기획으로 표시한다. 조합 수는 콘텐츠의 독창성이나 유튜브 정책 충족을 보증하지 않는다.

이번 변경은 기획 카탈로그, 순수 컴파일러, 계정별 기획·검토 저장 API와 DB 마이그레이션이다. 운영 DB 적용·배포·메뉴 연결·유료 생성 연결은 포함하지 않는다. 기존 30초·3분 생성 파이프라인과 10시간 생성 상태를 변경하지 않는다.

### 자료 구조

- `shared/healing-rain/intro-families.js`: 10개 소재 × 3개 기본 구도. 한국어 이름·설명, 영어 공간/구도/미세 움직임 프롬프트, 제외할 연출, 권장 본편을 버전과 함께 관리한다. 기존 `intro.js` 생성 경로와 분리된다.
- `src/lib/healing-rain/episodes.ts`: 엄격한 입력 검증 → 기존 본편 레시피 컴파일 → 인트로/본편/음향 프롬프트와 편집 지시 생성 → 저장된 회차 기획과 비교. 원본 `basePlan`은 기존 규칙 그대로 보존한다.
- `healing_rain_episodes`: 입력·카탈로그 버전·컴파일 결과·비교 결과를 불변 스냅샷으로 저장한다. 생성 시각과 ID는 서버가 부여한다. 수정은 새로운 요청 ID로 새 기획을 저장한다.
- `healing_rain_episode_reviews`: `approve_plan` 또는 `needs_revision`과 사람이 작성한 이유를 추가 기록한다. 기획 승인으로 미디어 생성·게시·정책 통과가 승인되지는 않는다. 이전 검토나 기획 스냅샷을 덮어쓰지 않는다.

소재: 구름 침대, 연꽃 침대, 수중 스위트, 꽃밭 침대, 거목 침실, 호수 유리 돔, 오로라 온실, 폭포 정원, 우주 정원, 진주 조개 침대. 30개 구도는 기획의 출발점이며 서로 다른 완성 콘텐츠 30개를 보증하는 수치가 아니다.

필수 입력은 `title`, `brief`, `intro`, `main`, `visual`, `audio`, `connection`이다. 실제 요청 예시는 `episode-input.example.json`을 참고한다.

- `brief`: 휴식 의도, 이번 편의 설정, 시청자가 실제로 다르게 느낄 경험. 의도는 인트로 프롬프트에 반영하고, 설정·차별점은 편집 검토에 보존한다.
- `intro`: 소재와 기본 구도. 새 제작은 새 원본 사용을 요구하며 같은 제작 안의 편집 수정은 허용한다.
- `main`: 기존 10개 본편 레시피의 입력 구조. 장대비/폭우, 야간 노출, 루프 동작 등 기존 방향 규칙을 유지한다.
- `visual`: 시선의 중심, 공간의 깊이, 새 장면의 구체적인 특징. 본편 이미지 지시에 반영한다.
- `audio`: 장면에 맞는 주 타격면, 듣는 위치, 거리감, 느린 강도 변화와 세부 표현. 예를 들어 열차는 유리와 낮은 주행음, 산사는 기와/돌과 처마 낙수, 연못은 흐르는 물 없는 수면 충격음을 사용한다. 천둥은 기본 비 음원과 분리해 기획하며 실행은 연결하지 않는다.
- `connection`: 빛/물/잎/보호받는 공간 중 연결 모티프와 이유. 구름을 억지로 움직여 인물을 가리는 대신, 소스 구도를 맞추고 편집에서 서서히 겹친다.

공통 인트로는 편안하게 잠든 성인, 따뜻하고 밝은 저대비의 공간, 안정된 침구와 미세한 호흡을 기본으로 한다. 15초 소스 중 6~15초에 9초 smoothstep dissolve를 적용하는 편집 지시를 저장한다. 인물 전체를 구름으로 덮는 조건과 생성 모델의 급격한 장면 변형은 사용하지 않는다. 본편은 인트로 1회 후 10초 전진 루프를 기획하고, 빗소리는 전환에서 다시 시작하지 않는다. 여기의 길이는 기획 값이며 실제 렌더가 수행된 상태가 아니다.

모든 경로는 로그인 검증을 먼저 수행하고 `Cache-Control: private, no-store`를 반환한다.

| `GET /api/healing-rain/episodes/catalog` | 10개 소재·30개 구도와 장면별 음향 선택 범위 |
| `POST /api/healing-rain/episodes/plan` | `{input}`을 서버에서 컴파일하고 본인 저장 이력과 비교. 저장 없음 |
| `POST /api/healing-rain/episodes` | `{clientRequestId,input}` 저장. 신규 201, 동일 요청 재시도 200 |
| `GET /api/healing-rain/episodes?cursor=...` | 본인 기획 50개씩 조회, `nextCursor`로 다음 페이지 |
| `GET /api/healing-rain/episodes/:id` | 본인 기획·당시 비교 결과·최근 검토 기록 20개 |
| `POST /api/healing-rain/episodes/:id/reviews` | `{clientRequestId,verdict,reason}` 추가 검토. 이유 12~1200자 |

생성과 검토 요청은 서로 별도의 요청 ID 영역을 사용한다. 같은 계정의 같은 요청 ID·같은 내용은 최초 결과를 재생한다. 다른 내용으로 요청 ID를 재사용하면 409, 다른 계정의 기획 또는 없는 기획은 404, 마이그레이션 미적용 시 503이다. 클라이언트는 user ID, 저장할 프롬프트, 비교 결과, 실행 승인 플래그를 제출할 수 없다. 본문 제한은 16KB다.

DB에는 강제 RLS와 소유자 조회 정책을 적용한다. 브라우저와 `service_role` 모두 직접 쓰기 권한이 없으며, 인증된 서버가 서비스 전용 RPC로만 저장한다. RPC는 요청별 트랜잭션 잠금을 사용한다. 마이그레이션은 Supabase의 기존 권한 있는 migration owner로 적용한다.

### 반복 기획 검토의 의미

최근 본인 회차 스냅샷 최대 100개를 비교한다. 현재 v1 회차 테이블만 대상으로 하며 기존 프로젝트·외부 유튜브·영상 픽셀·실제 음원은 비교하지 않는다. 비교 창이 제한되거나 지원하지 않는 이력이 있으면 명시한다.

본편 장소, 비 강도, 천둥, 카메라, 시선 중심, 공간 깊이, 타격면, 청취 위치, 음향 깊이, 강도 변화의 10개 범주를 비교한다. 전부 같으면 `needs_revision`, 나머지는 항상 `review_required`다. 80% 이상 같은 범주를 가진 기획도 검토 참고 목록에 표시한다. 이 비율은 내부 분류 기준이며 유튜브의 기준이나 안전 점수가 아니다. 제목·팔레트·시드·자유 설명·인트로 교체는 같은 본편 판정을 우회하지 않는다.

기획 검토 후에도 실제 생성 결과의 구도·인물·빛·속도·시청각 일치·반복 이음새를 검수해야 한다. 영상마다 사람의 판단을 없애는 기능이 아니라, 공통 규칙을 재사용하고 반복 기획을 일찍 발견하는 기반이다. 모델/프롬프트 버전, 원본 해시, 공급자 작업 ID, 편집 내역, 음원 구간 배열, 최종 렌더 해시를 후속 제작 기록에 연결하도록 요구 목록을 남긴다.

### 검증과 후속 연결

- 오프라인 테스트: 카탈로그 30개 구도와 본편 10개 조합 300건, 상한 입력, 반복 판정, 기존 생성 경로의 새 기획 거부, API 인증/소유권/재시도/페이지 조회.
- 격리 PostgreSQL 17.5(PGlite): 마이그레이션과 `scripts/healing-rain-episodes.regression.sql` 실행, 역할별 권한/RLS/불변 스냅샷/검토/잘못된 입력/롤백 검증. PGlite는 단일 연결이므로 동시 요청 스트레스 검증은 별도다.
- 후속 순서: 운영 DB 적용 → API 배포 → 회차 기획 UI 연결 → 새 기획을 읽는 비용 안내·생성 어댑터 → 30초·3분 실제 미디어 검수. 10시간 렌더 연결은 별도 단계로 유지한다.
